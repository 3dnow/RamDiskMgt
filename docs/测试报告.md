## 2. 实测推翻或修正的假设

| 原假设 | 实测结果 | 处理 |
|---|---|---|
| tmpfs 能 `mount -u` 改大小（网上说法） | 返回成功但大小不变；`-o size=` 报不支持 | 扩容统一做成热迁移 |
| 进程内 NSAppleScript 有约 5 分钟的授权缓存 | 7 次提权调用每次 3.5–6 秒，与每次都输入密码的耗时一致 | 每个操作的 root 命令合并成一个脚本；tmpfs 扩容改用不需要 root 的 ram:// 暂存盘，授权从 3 次降到 1 次 |
| AEA 口令加密可用任意长度密码 | scrypt profile 要求 ≥ 20 个字符 | 改为 PBKDF2-SHA256（60 万次）派生密钥 + symmetric profile，盐写进 authData |
| `hdiutil convert` 可以把加密镜像转成压缩格式 | 加密源镜像报 Permission denied | 改为硬链接暂存 + `diskutil image create from --encrypt` |
| 演示盘里 `cp` 出来的副本是 APFS 克隆 | 读 PRIVATESIZE 发现不是：macOS 的 `cp` 要加 `-c` 才克隆 | 改用 `cp -c` 造真克隆做对照（独占 0 字节、df 不变），据此实现克隆识别 |
| 测试里 `FileManager.copyItem` 能得到真实副本 | 在 APFS 上它默认就是克隆 | 测试改为按字节写出。这也说明 Finder 拷贝出来的同样是克隆，识别克隆是必要的 |
| 截图里侧边栏空白是界面 bug | 探针显示侧边栏表格有 8 行内容；换 CALayer 渲染也画不出来 | 判定为进程内截图画不出系统侧边栏材质，不是界面问题 |

## 2.1 字号放大（2026-10-09）

用户反馈“字体都太小了”。macOS 原生正文是 13pt，说明文字只有 10pt。

| 假设 | 实测 | 处理 |
|---|---|---|
| 用 SwiftUI 的 `dynamicTypeSize` 整体放大 | 在 macOS 上**完全无效**：caption 在 xSmall、默认、xxxLarge 下渲染尺寸都是 64×13 | 自建全局缩放：每种文字样式按 macOS 基准磅值乘以缩放比例 |
| 根视图设字体，所有控件都会继承 | 复选框、表单标签、输入框会继承；按钮、分段控件、下拉框的选中值**不继承**；`controlSize` 只让控件变高，不改字号 | 全局按钮样式把字号直接加到按钮文字上；分段控件改为自绘；下拉选项逐项设字号 |
| 弹窗（sheet）继承主窗口的设置 | 能继承缩放比例，但**不继承**默认字体和按钮样式 | 每个弹窗的根上再套一次缩放 |
| 列表行继承字体 | 侧边栏和树形勾选列表的行**不继承** | 行内文字显式设置字号 |
| 系统空状态视图能缩放 | `ContentUnavailableView` 的字体是固定的 | 换成自绘的空状态视图 |

默认缩放 1.3（正文约 17pt）。在“设置”里可调 0.9–2.0 倍，也支持 ⌘+ / ⌘- / ⌘0。在 1.0、1.3、1.75 三档下截图检查过布局：1.0 与改动前一致，1.75 下没有截断或重叠。

顺带修掉一个原有 bug：盘没有备份时，“备份与还原”页的标题和按钮会被挤到页面中间。

## 2.2 事故：从备份重建后还原失败、盘推不出（2026-10-15）

用户操作：备份库 → 重建为新盘，还原失败；在 RamDiskMgt 里推出失败，在 Finder 里推出也失败；点“强制推出”后才成功。

**证据**（经用户同意读取）
- 应用数据目录：那份备份是从外部导入的加密 DMG（约 450MB，由别的工具生成）。清单里记录的内容大小为 0。
- 系统日志（前后约一分钟）：
  - 还原时 copyfile 报 `No space left on device`；
  - 之后 7 次普通卸载全部失败，`unmount call returned (status code 0x0000001C)`，即 ENOSPC；
  - 期间没有任何进程拒绝卸载（无 dissent 记录）；
  - 最后 Finder 用强制选项（0x80000）卸载成功，随后设备也推出成功。

**结论**

| 问题 | 机制 | 状态 |
|---|---|---|
| 新盘太小 | “重建为新盘”的默认容量 = max(原盘容量, 内容×1.25+128MB)；导入的备份内容记为 0，结果只给 128MB，而且没有任何检查 | 已修 |
| 报错误导 | AEA 写满时 AppleArchive 只返回 “ArchiveError error 0”，旧代码一律报“备份文件损坏” | 已修 |
| 推不出 | 卸载返回 ENOSPC，不是有进程占用 | 机制确认，**触发条件未复现**（见下） |
| 强制推出的副作用 | 日志显示卸载和设备推出都成功，ram:// 设备已释放；RAM 盘推出后内容本来就清除 | 无副作用 |

**未能复现的部分**：以下几种满盘状态，普通卸载都成功：
- 写满到连新建文件都失败（APFS 还保留 1.77MB）；
- 照现场重放：约 450MB 中小文件写入 128MB 可见盘，失败后等 9 秒再卸载；
- 写满后等 15 秒，盘可见或隐藏两种情况。

所以“卷满了”与“卸载 ENOSPC”只是相关，真正的触发条件还不清楚。

**修复**
- 还原前预检空间：按 4KB 块对齐、每个条目另加 4KB 元数据估算，再留 16MB 余量；放不下就在写入前报“空间不足”。
- 从备份重建（包括“已保存配置 → 重建”和启动时自动还原）时，先读备份内容，按内容计算推荐容量，配置偏小就自动调大并提示。“重建为新盘”弹窗读取备份后才允许选容量，下限就是推荐值。
- 导入的备份读过一次内容后，把文件数和大小补记进清单。
- 写满时报“空间不足”，不再误报“备份文件损坏”。
- 推出失败且没有占用进程时，说明原因并提供“强制推出”；同时把可用空间、inode、错误原文、所有占用进程（含系统进程）写进 `logs/eject.log`，作为下次复现时的证据。
- 推出前的自动备份如果失败，会先询问再推出，不再直接中止推出。

**验证**
- 集成测试 `RestoreSpaceTests`：
  - 放不下时，AEA 和 DMG 都在写入前报空间不足，目标盘保持为空，之后能普通推出；
  - 跳过预检直接写满时，两种格式都识别为空间不足；
  - 按推荐容量新建的盘，小文件、中等文件、大文件三种内容都能完整还原，剩余空间 ≥ 128MB。
- GUI 自检新增一步：导入一份大小未知的备份，用 64MB 配置重建，容量被自动调到 192MB，内容完整还原。
- 探索性探针保留在 `RestoreFailureProbe.swift`，设置 `RDM_PROBES=1` 才运行。

## 2.3 复查与“新建时提示盘不存在”（2026-10-15）

**新建 / 重建时闪“RAM 盘已不存在”**
- 机制：盘建好后界面立即切过去，但盘列表要等整个操作结束才刷新；“从备份重建”要等还原也完成。扩容切换的瞬间，底层列表也会短暂查不到这块盘。
- 探针（`RamDiskMgt --probe-create-gap`，每 20ms 采样“选中了、但列表里查不到”的时长）：

| 场景 | 修复前 | 修复后 |
|---|---|---|
| 普通新建 | 0.04 秒 | 0 |
| 从约 300MB 的 DMG 备份重建 | 1.47 秒 | 0 |
| 扩容（每 30ms 强制刷新） | 底层列表 70 次轮询中有 7–8 次查不到 | 界面空窗 0 |

- 修复：建好的盘立即放进列表；扩容期间保留该盘的条目；用量刷新时核对 statfs 的挂载点，避免在切换瞬间读到上一级目录所在磁盘的容量。

**代码复查发现并修复**（自查加独立审查，每条都对照代码或实测确认过）

| 问题 | 证据 | 修复 |
|---|---|---|
| 外部 AEA 备份（系统 aa + aea 生成）完全读不了，列目录直接报 ioError | 实测：系统 `aa archive` 的输出是压缩过的（文件头 “pbze”），解密后要再解压一层 | 外部归档自动判断是否解压；列目录时从每个条目头读出真实大小和类型（原来全部记为 0，预检形同虚设，会让 10-15 的事故原样重演） |
| 推出时取消管理员授权，被当成“无法推出”，还提供强制推出 | 读代码 | 兜底只针对 ram:// 盘上 diskutil 的失败；用户取消不再写诊断日志 |
| 兜底文案在没有证据时说“强制推出不会造成其他影响” | lsof 以当前用户运行，看不到管理员或其他用户的进程 | 只有剩余空间确实不足时才这样说；有占用程序就列出来；否则用中性说法 |
| tmpfs 预检把将被删除的文件算作可用空间 | 实测 tmpfs 删除后要几分钟才回收 | tmpfs 不计回收空间。APFS 实测会先删后写（剩 59.9MB 能覆盖 70MB 文件），合并模式继续计入 |
| 重建时“已自动调大容量”会盖掉“部分文件还原失败” | 读代码：两次给 alert 赋值，后一次覆盖前一次 | 合并成一条提示 |
| 重建时 DMG 被重复挂载读取 3–4 次 | 读代码 | 读出的条目一路传下去，总共挂载两次 |
| “替换”在确认备份完整之前就清空目标 | 实测：AEA 损坏位置在 30%/60%/90% 时只读清单能通过，完整校验失败 | AEA 先完整校验再清空；DMG 挂载成功后才清空，并复用同一次挂载。测试：后段损坏的备份做替换还原，原内容保留 |
| 盘被推出后，还原可能写进启动盘上的挂载点目录 | 读代码：statfs 落到上一级文件系统 | 还原前核对目标仍是挂载点根；还原期间开着目标根目录，Finder 的普通推出会因占用失败。测试：目标不是挂载点时拒绝、不写入 |
| 本工具正在读写某块盘时，菜单栏、右键菜单仍可推出它 | 读代码 | 按盘记录进行中的操作，所有推出入口都检查；定时自动备份也避开忙碌的盘。GUI 自检覆盖 |
| 两个确认框同时出现，前一个永远挂起，按钮一直灰着 | 读代码 | 确认框排队逐个弹出。GUI 自检覆盖 |
| 提示框会被新提示直接替换，前一条内容丢失 | 探针 G 组 | 提示框排队，改用现行的 alert 接口 |
| 开机自动创建时读不出备份，整块盘都不建 | 读代码 | 退回建空盘并说明原因；自动调大的容量写回配置。GUI 自检覆盖 |
| 回收空间按逻辑大小计算，遇到硬链接、克隆、稀疏文件会高估 | 读代码 | 按实际占用块数计算，同一 inode 只算一次，克隆只算独占部分；合并模式不计多链接文件。测试覆盖 |
| tmpfs 可能按 16KB 页分配，按 4KB 估算会偏小 | 推测，未在 tmpfs 上实测 | 估算使用目标卷的块大小；新建 tmpfs 按内存页大小估算（保守方向） |
| DMG 空间不足时推出镜像两次，可能误推出复用了同一设备号的盘 | 读代码 | 只推出一次 |
| 外部空归档被误判成“需要解压” | 读代码 | 区分“读到结尾”和“读取出错”。测试覆盖 |
| 重建弹窗、已保存配置页的密码状态会错位 | 读代码 | 读取时固定当时的密码；切换备份时清空密码；钥匙串里有密码时也能手动输入 |

**自检崩溃排查**：自检曾在 3 次里崩溃 2 次（段错误，位于 SwiftUI 关闭提示框的动画里）。用探针逐组对照：

| 组 | 操作 | 结果 |
|---|---|---|
| A | 只有确认框，快速弹出、回答 | 30 轮无崩溃 |
| B | 提示框刚关掉马上弹确认框 | 30 轮无崩溃 |
| C | 提示框完整显示后用代码关掉 | 8 轮无崩溃 |

## 2.4 备份：第一次失败、没有进度、钥匙图标不一致（2026-10-20）

用户反馈三点：第一次备份失败，重试才成功；备份没有进度；两份备份都设了密码，但只有一份带钥匙图标。

**证据**（经用户同意，只读应用数据目录和 10-19、10-20 两天的系统日志）
- `backups.json`：两份都是 DMG 整盘加密备份，第一份 `passwordInKeychain=false`，第二份为 `true`。
- `logs/` 目录不存在：当时 App 不记录操作失败。
- 两次备份所在的两天里，系统日志只有一次钥匙串写入（`SecItemAdd`），时间与第二份备份完成时一致。
- 第一份备份那天，App 运行期间生成映像的系统服务 diskimagesiod 只启动过一次，在成功那份开始后 7 秒；再往前一次启动是 8 小时前。
- 备份窗口打开期间钥匙串被反复查询（例如连续 5 秒，每秒都有）。旧代码在窗口的 `body` 里读钥匙串，每次重绘（包括每输入一个字符）都会查一次。

**进度探针**（`BackupProgressProbe`，统计一次备份收到的进度回调）

| 格式 | 修复前（60 × 4MB） | 修复后（同一份数据） | 修复后（12 × 25MB 不可压缩随机数据） |
|---|---|---|---|
| AEA | 2 次（扫描 1、收尾 1），写入阶段 0 次 | 3 次，写入阶段 1 次 | 3 次，写入阶段 1 次 |
| DMG | 3 次（准备 1、写入 1、收尾 1），百分比只有 0 和 100 | 71 次，百分比 0、5、7、8、9、10… | 36 次，百分比 0、5、10、16、23… |

AEA 修复后写入阶段仍只有 1 次，是因为这两份数据 0.1–0.2 秒就写完了，而界面进度限流为 0.1 秒一次。写入进度本身由单元测试在关闭限流后验证（见“验证”）。

另外单独写了一个 AppleArchive 小程序对照：3 个 150MB 文件加 20 个小文件，`encodeWriting` 消息 1763 次，全部只出现在 `encodeStream` 的回调里；`writeDirectoryContents` 的回调只收到扫描消息，每个文件 1 次。

**结论**

| 问题 | 机制 | 状态 |
|---|---|---|
| DMG 没有进度 | `diskutil image create` 把 `[NN% completed]` 写在 stderr 上，旧代码只解析 stdout | 已修 |
| AEA 没有进度 | 旧代码在 `writeDirectoryContents` 的回调里等写入消息，而写入消息只发给 `encodeStream` 的回调 | 已修 |
| 看不到发生了什么 | 点“备份”后窗口立即关闭，进度只在主窗口底部一行小字里，出错只弹一个提示框 | 已修：窗口一直开着，显示阶段、进度条、已处理大小、速度、耗时；可取消，也可以放到后台；结束后显示结果（文件数、大小、密码是否已存、文件位置）或错误原文和“重试” |

**写满时无限重试**（集成测试 `engineReportsOutOfSpaceNotCorruption` 卡死）
- 现象：测试盘写到只剩 3MB，两个线程一直在 `copyfile_data` 里循环，调用来自新加的大文件进度回调。
- 机制：回调对所有阶段都返回 `COPYFILE_CONTINUE`。`man copyfile` 写明，数据回调在出错时返回 CONTINUE 会重写同一块数据。盘满时每次都失败，于是无限重试。真实使用中往快满的盘上扩容、还原都会卡住。
- 修复：`COPYFILE_ERR` 阶段记下 errno 并返回 `COPYFILE_QUIT`，上层照常识别为空间不足。对照：修复前卡住超过 10 分钟，修复后 26 秒通过。

**tmpfs 自检的“无提示”**
- 不是提权改到后台队列造成的：用 `RDM_APPLESCRIPT_MAIN_THREAD=1` 退回主线程，同样失败。
- 不是 App 失去焦点造成的：APFS 自检期间每 0.4 秒把 Finder 切到前台，提示出现时 App 都不在前台，仍然 33/33。
- 埋点显示提示都正常弹出，并且都是被按钮点击关掉的。自检用代码点击时 App 不在前台；失败那一次被点掉时 App 在前台。测试者确认输完密码后点过提示框：提示被人先点掉，自检再去读时已经没了。属于测试操作问题，测试指南已注明自检期间不要点提示框。

**提权方式**：苹果的线程安全说明（归档文档）把 NSAppleScript 列为只能在主线程使用的类，分支却把它放到了后台队列。虽然实测可用，但偶发问题很难测出来，所以最终改为 App 也用 `osascript` 子进程执行管理员命令，删除了进程内 NSAppleScript 的实现。

**切换耗时**：对照 main 与本分支的 rdmctl，同样 256MB → 384MB 扩容，切换耗时都在 0.9–1.1 秒，没有退化。README 里“约 0.1 秒”是早期在另一种负载下测的。

## 3. 未解决的问题

1. **加密 DMG 偶发 “Disk image operation failed with error code 156”。** 在 12 次包含 DMG 用例的测试运行里出现过 1 次，当时正与集成测试的 ram:// 挂载/推出并发；单独跑 3 次、4 个 DMG 并发创建都没有复现。原因未知。已加探针：失败时自动用 `--verbose` 重试一次，两次的输出都写进 `logs/dmg-create.log`。下次复现就有一手日志可以分析。
